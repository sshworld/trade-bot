# 429 vs 418 — Binance docs, decision, implementation (TA review 2026-10-21 18:04 KST)
Branch r4-testnet-findings (from 4588887). Nothing deployed.

## B. Official documentation (quoted)
USDⓈ-M Futures General Info — https://developers.binance.com/docs/derivatives/usds-margined-futures/general-info
(section "HTTP Return Codes" / "IP Limits"; the page is behind a JS bot check for scripted fetches, quoted via the
search index of the same page, also https://developers.binance.com/docs/derivatives/usds-margined-futures):
> - HTTP `429` return code is used when breaking a request rate limit.
> - HTTP `418` return code is used when an IP has been auto-banned for continuing to send requests after receiving `429` codes.
> - When a 429 is received, it's your obligation as an API to back off and not spam the API.
> - Repeatedly violating rate limits and/or failing to back off after receiving 429s will result in an automated IP ban (HTTP status 418).
> - IP bans are tracked and scale in duration for repeat offenders, from 2 minutes to 3 days.
> - The limits on the API are based on the IPs, not the API keys.
> - It is strongly recommended to use websocket stream for getting data as much as possible …

Retry-After (Binance derivatives Portfolio-Margin-Pro General Info
https://developers.binance.com/docs/derivatives/portfolio-margin-pro/general-info and Spot REST API
https://github.com/binance/binance-spot-api-docs/blob/master/rest-api.md — the futures page has no separate sentence):
> - A `Retry-After` header is sent with a 418 or 429 responses and will give the number of seconds required to wait,
>   in the case of a 429, to prevent a ban, or, in the case of a 418, until the ban is over.

Reading:
* 418 = the IP is banned (not an endpoint or a key) → every request from that IP, order placement / cancel / close
  included, is refused until Retry-After. The docs do not state literally "requests during a ban extend it", but bans
  "scale in duration for repeat offenders" and 418 is defined as the response to *continuing to send* after 429s →
  any request during the ban cannot succeed and can only count against us.
* 429 → continuing (not backing off) escalates to a 418 ban. Retry-After on a 429 = time to wait to PREVENT a ban.
  The docs give no exemption for orders/cancels.

## Decision (TA rule)
* 418: NO REST call at all until Retry-After (critical included). 🚨 at once. Protective actions (lost-stop
  replacement, reduceOnly close after a mark cross) are queued and sent on the first tick after the ban (loop ≈ 1 s).
  The exchange stop is the only protection during a 418.
* 429: non-critical calls refused locally (entries blocked, no polling, no reconcile); critical protective calls still
  go out, only when triggered (event-driven: a lost stop or a mark cross) — a handful of requests, not polling.
  Residual risk noted for TA: per the docs, sending during a 429 window can escalate to 418; we accept it only for
  protective actions.

## Implementation (exchange.py / engine.py)
* `BinanceREST.ban_until` (418 only): `_req` refuses EVERY request while banned (`RateLimited … IP ban … (not sent)`);
  `on_rate_limit(status, retry_after)` hook → engine 🚨 immediately on a 418.
* `V6Engine.stop_monitor` (user stream ORDER_TRADE_UPDATE and ALGO_UPDATE — Binance conditional/stop orders are algo
  orders, so their CANCELED/EXPIRED arrives as ALGO_UPDATE): an open position's stop (client id `{cid}p` / `{cid}s<n>`)
  CANCELED / EXPIRED / REJECTED that we did not cancel ourselves (every `x("cancel")` records its client id) → 🚨,
  `pos.stop_lost` persisted, ONE replacement stop (same price; closePosition, or a qty stop if the lost one was a qty
  stop). 418 → queued. Failed → 🚨 + mark-cross fallback. REST reconcile clears `stop_lost` once a stop is confirmed.
* Mark stream: `stop_lost` and mark ≤ original stop → `close(sym, "stop_lost_breach")` at once (no grace — there is
  no exchange stop). 418 → `closing` set + queued.
* `close()` during a 418 queues instead of looping; `check_api_dead` never flattens during a 418;
  `tick()` → `flush_queued()` first thing once the ban is over.
